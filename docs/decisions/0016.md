# ADR 0016: Keep explicit library composition in Ternfold 0.2

Status: accepted for Ternfold 0.2.

## Decision

Keep 0.2 composition as pure `step` calls, explicit `Decision` matches, explicit
outer snapshot selection and ordered list concatenation. No-go for first-class
jointly accepted machine groups or static transition assertions in 0.2.
Use ordinary runtime conditions for relationships between proposed values.

The [bounded experiment](../composition.md) implements a C17 group
model independently of production and compares it with actual existing Ternfold
source through both verified-Core executors. Its 225 bounded inputs agree in the
restricted total domain. Counterexamples establish that flattening child steps
is not a semantics-preserving replacement in the presence of faults.

## Alternatives and observed distinction

1. Explicit library composition: finish child A, finish child Z, inspect their
   decisions, reject with the original pair or concatenate accepted emissions.
   An accepted inner result remains private ordinary data. A caller can instead
   match A before calling Z; that is a different, expressible evaluation policy.
2. Opaque grouped calls: execute complete child steps in a specified order,
   retain all values privately, then combine decisions. This can reproduce a
   particular library policy but gives no demonstrated additional capability.
   Cross-member candidate projections are unavailable from a rejected child.
3. Flattened groups: schedule all member candidates before any member guard and
   defer all emissions until joint acceptance. The prototype implements this
   hypothesis, with explicit finite DAG admission and runtime total assertion.
   It changes deterministic fault and rejection precedence compared with (1).
4. Static relationship contracts: no proof engine or sound contract language is
   implemented. Exhaustive bounded enumeration and runtime guards do not prove
   arbitrary Int programs, recursive calls, divergence or all transitions.

Actual paired source observations: an early child emission, predicate or
rejection-reason division faults R002 before a later child's overflow in the
library program. A corresponding flattened two-cell machine faults R001 in its
candidate first. An early rejection plus a later faulting emission yields R002
with eager library calls, while the flattened machine returns the rejection.
Both executors suppress all staged output on every tested runtime fault.

## Consequences

Nested rejection provenance remains an application choice: wrap member identity
and its typed reason in a user enum, retain both original snapshots on outer
rejection, and discard private inner accepted values/emissions. Never turn a
runtime fault into a catchable rejection. The sample uses a nominal `Joint`
enum with a member ID and Int guard reason; heterogeneous machines would require
distinct typed cases, not structural layout coercion.

Emissions remain ordered values. Two commands for destination 7 are not a
compiler conflict: the fixture retains `1,1,2,2`, and explicit reversed
concatenation produces `2,2,1,1`. First/last wins, rejection, deduplication and
coalescing are different application policies. A group feature would have to
specify its order and conflict policy before claiming automatic composition.

Existing `next.cell` dependencies remain lexical, including dead branches;
ASCII ready-name order determines faults. A flattened group would need a stable
qualified identity and ordering for every member/cell, exact dependency
extraction before optimization, duplicate-writer rules, cycle diagnostics and a
decision about access to candidates of a rejecting member. Opaque `step` calls
cannot supply those projections merely by reordering ordinary function calls.

If revisited, require a separate task and normative ADR specifying opaque versus
flattened semantics, eager versus short-circuit rejection, typed nested reason
paths, guard order, emission order/publication, dependency scope, name ordering,
divergence and first-fault precedence. Specify assertion timing, its rejection
type and checked arithmetic separately from any static proof. Review the full
syntax/AST/resolution/type/plan/lowering/verifier/executor/diagnostic impact and
source-span identities. Production work has not been opened by this experiment.

## Verification

The bounded composition model and paired Ternfold fixtures are part of the
strict and sanitizer CI checks. See [testing](../testing.md) for commands and
[composition](../composition.md) for the model's scope. The experiment adds
no production syntax, Core operation or CLI command.
